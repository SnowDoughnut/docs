## Core sections

### 1. Value proposition

**One sentence, in the reader's language: what does the brand do, for whom, and why does it beat the alternative?**

_E.g. Doughnut Labs turns the process you're running in a spreadsheet into something that runs itself, and you can have it live this afternoon._

<Accordion title="Concept review: Value proposition">
  This is the positioning statement translated for someone outside the company. The position is written to be testable and is full of internal vocabulary. The value proposition has to survive being read once, by a distracted person, with no context.

  What tends to get lost in the translation is the "instead of what" part. A value proposition that describes what the product does, without any signal of what it replaces or improves on, reads as accurate and gives a reader no reason to move. The comparison doesn't have to be explicit, but it usually has to be implied.

  It's also worth separating this from a tagline, which sits in section 3. A value proposition is judged on clarity. A tagline is judged on memorability. Asking one sentence to do both usually costs it the first.
</Accordion>

### 2. Message pillars

Three is the usual number. Each pillar is a supporting argument for the value proposition, and each needs its own proof.

#### Pillar 1

| Field | Fill in |
| :-- | :-- |
| Pillar | _E.g. Live in an afternoon_ |
| What it means | _E.g. There's no implementation project, no admin approval, and no data migration before the first process runs._ |
| Proof | _E.g. Median signup-to-live time is 3.5 hours. 71% of accounts are set up by the process owner._ |
| Where it leads | _E.g. Free trial, no demo required._ |

#### Pillar 2

| Field | Fill in |
| :-- | :-- |
| Pillar | _E.g. It holds up as you grow_ |
| What it means | _E.g. The thing you build in an afternoon is the same thing running a year later, not a prototype you replace._ |
| Proof | _E.g. Named customer scaled from 1 process to 40 without a rebuild._ |
| Where it leads | _E.g. Case study, pricing page._ |

| Where it leads | _E.g. Product tour._ |

<Accordion title="Concept review: Message pillars">
  Pillars exist because one sentence can't carry a whole argument, and because a brand that says a different thing every campaign never accumulates anything in a buyer's memory. Repetition across a small set of ideas is what builds recognition; variety across many ideas is what prevents it.

  The count matters less than the discipline. Three is common because it's roughly what a team can hold in their heads and what a market can absorb, but the reason to cap it is that an uncapped list stops functioning as a filter. Once there are nine pillars, every idea fits one of them, and the document has stopped saying no to anything.

  There's a real tension in the "where it leads" column. Tying each pillar to a destination makes the messaging immediately usable by campaign teams. It can also flatten a brand-level idea into a funnel step. Which risk matters more depends on whether this document is read mostly by strategists or mostly by people shipping ads next week.
</Accordion>

### 3. The message set

The same idea at four lengths. Each is used in different places, and each should be recognizably the same argument.

| Format | Length | Fill in |
| :-- | :-- | :-- |
| Tagline | 3 to 8 words | _E.g. Live this afternoon._ |
| One-liner | One sentence | _E.g. Doughnut Labs turns a spreadsheet process into something that runs itself, live in an afternoon._ |
| Elevator pitch | 30 seconds, spoken | _E.g. Most ops teams run their core processes in a spreadsheet until it breaks. The usual fix is a workflow platform, which means a three-month implementation and a systems admin. Doughnut Labs sits in between: you build the process yourself, it's live the same day, and it still works when you're running forty of them._ |
| Boilerplate | 40 to 60 words, third person | _E.g. Doughnut Labs helps operations teams move core processes off spreadsheets without an implementation project. Teams build and launch a working process in an afternoon, then change it themselves as it grows. Founded in 2019, Doughnut Labs is used by more than 4,000 teams._ |

<Accordion title="Concept review: The message set">
  These four formats exist because the same argument has to survive very different amounts of room. A press release footer, a conference badge, a sales call, and a homepage subhead each allow a different word count, and a message that only works at one length gets improvised at the others.

  Improvisation is the actual risk. When there's no approved 30-second version, five salespeople invent five of them, and the market hears five slightly different companies. Writing each length down once is less about elegance than about removing the need to make it up under pressure.

  The tagline is the one most likely to be argued about and the least likely to matter on its own. Brands differ enormously in how much weight they put on it, and a memorable tagline attached to a position nobody can state is a decoration. The pillars are what the tagline is compressing, which is why this section sits after them.
</Accordion>

### 4. Audience variations

Same pillars, different emphasis. One row per audience you address differently.

| Audience | What they care about most | Lead with | Don't lead with |
| :-- | :-- | :-- | :-- |
| _E.g. Ops lead (buyer)_ | _Getting the process off the spreadsheet this quarter_ | _Live in an afternoon_ | _Long-term scale_ |
| _E.g. Their manager (approver)_ | _Whether this becomes a mess in a year_ | _It holds up as you grow_ | _Speed, which reads as a shortcut_ |
| _E.g. IT (blocker)_ | _What they'll be asked to support_ | _You own it, not IT_ | _No admin needed, which sounds like a bypass_ |
| \[add audience\] |  |  |  |

<Accordion title="Concept review: Audience variations">
  The distinction this section rests on is between varying emphasis and varying substance. Reordering the same three pillars for a different reader keeps one company talking. Giving each audience its own argument produces several companies wearing the same logo, and buyers who talk to each other notice.

  The "don't lead with" column often does more work than the one next to it. The same true statement can land completely differently depending on who reads it: a claim that reassures a buyer can read as a threat to whoever would otherwise have owned the decision. Naming that in advance is cheaper than discovering it in a deal.

  How many audiences belong here is a judgment about cost. Every row is another thing to keep current, and a matrix with twelve audiences tends to go stale in a way one with three doesn't.
</Accordion>

### 5. Approved claims

What the brand is allowed to say, and under what conditions. Anything not cleared here needs review before it ships.

| Claim | Status | Evidence | Conditions |
| :-- | :-- | :-- | :-- |
| _E.g. "Live in an afternoon"_ | _Approved_ | _Median 3.5 hours, product analytics_ | _None_ |
| _E.g. "4,000\+ teams"_ | _Approved_ | _Billing data, refreshed quarterly_ | _Round down, never up_ |
| _E.g. "The fastest way to..."_ | _Not approved_ | _No competitive benchmark_ | _Superlatives need legal review_ |
| _E.g. "Used by \[named customer\]"_ | _Conditional_ | _Signed reference agreement_ | _Named logos only from the approved list_ |
| \[add claim\] |  |  |  |

**Who approves a new claim, and how long does it take?**

_E.g. Brand lead approves wording. Anything comparative or numeric also goes to legal. Two working days._

<Accordion title="Concept review: Approved claims">
  A claims list is where messaging meets risk, and it serves two audiences that want different things from it. A writer wants to know quickly whether a sentence is usable. A reviewer wants to know what the sentence is standing on. A single table with a status column and an evidence column answers both without a separate approval thread each time.

  Claims decay in a specific way that's easy to miss: the sentence stays the same while the number behind it moves. "4,000 teams" was accurate when someone wrote it, and nothing about the sentence signals that it needs rechecking. Attaching a refresh cadence to the evidence is what catches that.

  The conditions column is where most of the nuance ends up. Few claims are simply allowed or forbidden, and the interesting cases are the ones that are fine in one context and not in another.
</Accordion>

## Optional sections

### A. Objection responses

<Tip>
  Optional: include if the brand has a sales motion, or if the same hesitation shows up repeatedly in support and comments
</Tip>

| Objection | What's behind it | Response |
| :-- | :-- | :-- |
| _E.g. "This looks too simple for us"_ | _Fear of outgrowing it_ | _Point at pillar 2 and the named customer running 40 processes._ |
| _E.g. "We already have a platform"_ | _Sunk cost, not satisfaction_ | _Ask which processes still live in spreadsheets alongside it._ |
| \[add objection\] |  |  |

<Accordion title="Concept review: Objection responses">
  An objection is usually a compressed version of a longer worry, and answering the compressed version tends to miss. "Too simple for us" is rarely a request for a feature list; it's a prediction about a rebuild in eighteen months.

  Writing the underlying worry in its own column stops the response from becoming a rebuttal. A rebuttal argues with the sentence the person said. A response addresses the thing that made them say it, which an existing pillar often already covers.
</Accordion>

### B. Competitor language

<Tip>
  Optional: include if competitors are named in market, in sales conversations, or in comparison pages
</Tip>

**How does the brand talk about named competitors? What's off-limits?**

_E.g. Doughnut Labs names competitors only on comparison pages, describes what they're genuinely good at before drawing the contrast, and cites their public pricing verbatim. No claims about competitor performance, reliability, or internal practices._

<Accordion title="Concept review: Competitor language">
  Brands sit at very different points here and several work. Some never name a competitor, on the view that it lends them attention. Others build a whole acquisition channel out of comparison pages and win the buyers who were going to run the comparison anyway.

  The consideration that cuts across both is that comparative claims carry a different evidentiary burden than claims about yourself. Describing your own product optimistically is ordinary marketing. Describing a competitor's inaccurately is a different category of problem, and it's also the version a reader is most likely to check.
</Accordion>

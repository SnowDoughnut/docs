_Build the schema below as a plain spreadsheet. Examples use Doughnut Labs, a SaaS company that sells disruptive Doughnut Technology, modelled here as its direct-to-consumer arm so the numbers have orders and revenue behind them._

<Note>
  Copy the blank template ([spreadsheet](https://docs.google.com/spreadsheets/d/19uHFbXOlrPPh5FgEbqFfPrB0P8mnwtswCxVKZzt6tag/export?format=xlsx) or [CSV](https://drive.google.com/uc?export=download&id=1sGO2aQvigQ1E8Vcfro09PxmDae6Gdg3m)) into your own spreadsheet and start filling in rows each day through the scheduled daily fill, or each week by hand. Nothing about the structure changes when you add a channel or a metric; you just add rows. See [data quality and rollup concepts](/data-quality-and-rollup-concepts) for why this shape, one row per metric, works better than the wide table most people picture first.
</Note>

## Why one row per metric

Most people picture a metrics table like this, metrics down the side, dates across the top:

| Metric | Week of 06-01 | Week of 06-08 | Week of 06-15 |
| :-- | :-- | :-- | :-- |
| Ad spend | \$61,400 | \$58,200 | \$63,900 |
| Impressions | 1,204,300 | 1,180,900 | 1,251,600 |

That's a fine way to look at data. It's a poor way to store it, because adding a second channel means either a second table, a second header row, or metric names that awkwardly embed the channel (`Ad spend (Meta)`, `Ad spend (Google)`). Every one of those breaks the moment you add a third channel.

The fix is to store one row per date, channel, and metric instead:

| Date | Channel | Metric | Value |
| :-- | :-- | :-- | :-- |
| 2026-06-01 | meta | ad_spend | 8770 |
| 2026-06-01 | meta | impressions | 172040 |
| 2026-06-01 | google_search | ad_spend | 4130 |

Nothing about this structure changes when a channel or a metric gets added. You add rows, never new columns. The wide table at the top of this page is one pivot table away from this format; it's a view you generate, not the thing you store.

## The schema

Fifteen columns, in two blocks. The **core** eight describe the measurement. The **dimension** seven say what was being measured, and they are what every naming convention in this knowledge base exists to fill. Each row covers one day, so a report over any date range, such as October 2 to November 1, is a filter, never a restructure.

<Info>
  The core eight are the same for every business. Some of the dimension columns only earn their place in some businesses: `product` matters once you sell more than one thing, and `attributed_date` matters once results arrive later than the spend that caused them. Leave a column out until you need it, and add it from the day you do. See [which columns your business needs](#which-columns-your-business-needs).
</Info>

### Core columns

Always filled in, on every row.

| Column | What it holds | Example |
| :-- | :-- | :-- |
| `date` | The day this row covers, `YYYY-MM-DD` | `2026-06-08` |
| `grain` | What this row measures: `channel`, `campaign`, `ad_group`, or `ad` | `campaign` |
| `channel` | Lowercase channel name, or `blended` for business-level numbers | `meta` |
| `metric` | Lowercase metric name, matching a metric in your [data dictionary](/marketing-reporting-data-dictionary) | `ad_spend` |
| `value` | A bare number: no currency symbol, no comma, no percent sign | `172490.55` |
| `unit` | `currency`, `count`, `ratio`, `percent`, or `days` | `currency` |
| `source` | Where the number came from | `meta_ads` |
| `is_estimate` | `true` or `false`; whether the number is still unreconciled | `false` |

### Dimension columns

Filled down to the row's grain, blank below it. Leave them genuinely blank, not `n/a` or `-`, so a filter for "blank" works.

| Column | What it holds | Filled at grain |
| :-- | :-- | :-- |
| `campaign` | The platform campaign name, exactly as it appears in the platform | `campaign` and below |
| `ad_group` | The ad set / ad group / variant name | `ad_group` and below |
| `ad` | The ad name | `ad` only |
| `product` | The product identifier from your [product pages](/product-catalog) | `campaign` and below |
| `experiment_id` | The experiment or pilot ID, blank if the row is neither | Wherever the test runs |
| `attributed_date` | The date this result is **credited to**, when that differs from the date it happened. Blank on ordinary rows | Any |
| `notes` | Optional, anything worth flagging on this specific row | Any |

Each of these has exactly one source, and none of them is typed by hand at report time:

| Column | Comes from |
| :-- | :-- |
| `campaign` | [Campaign naming conventions](/campaign-naming-conventions), matching `utm_campaign` character for character |
| `ad_group` | [Ad set / ad group / variant naming conventions](/ad-set-group-naming-conventions), matching `utm_content` |
| `ad` | [Ad naming conventions](/ad-name-conventions) |
| `product` | The product segment of the campaign name, split out at import. See [product pages](/product-catalog#before-you-start) |
| `experiment_id` | The [experiment ID](/experiment-id-convention) or [pilot ID](/pilot-brief) appended to the name at the level the test targets |
| `attributed_date` | Your CRM or analytics platform, from the stored source fields on the record. See [where the values get stored](/utm-standards#7-where-the-values-get-stored) |

<Warning>
  **Never sum across grains.** A day has an `ad_spend` row at channel grain and several more at campaign grain, and they describe the same money. Adding them together double-counts it. Filter to a single `grain` value before adding anything up, every time, exactly as you already filter to a single period.
</Warning>

### Lagging outcomes and the date they belong to

Some results arrive long after the spend that caused them. A deal closing in June was often generated by leads, and budget, from March. Two pages in this framework tell you to report those against the period that generated them rather than the period they landed in, and this is the column that makes that possible.

| Column | Answers |
| :-- | :-- |
| `date` | When did this happen? |
| `attributed_date` | Which day's effort is it credited to? |

On an ordinary row the two are the same thing, so `attributed_date` stays blank. On a lagging outcome they differ, and both are needed: the close date is a fact about the deal, the attributed date is what lets the cost per result be calculated against the spend that produced it.

**A closed deal, closing in June, generated by March's leads:**

| date | attributed_date | grain | channel | metric | value | unit |
| :-- | :-- | :-- | :-- | :-- | :-- | :-- |
| 2026-06-08 | 2026-03-09 | channel | google\_search | closed\_won | 0.6 | count |
| 2026-06-08 | 2026-03-09 | channel | linkedin | closed\_won | 0.4 | count |
| 2026-06-08 | 2026-03-09 | channel | google\_search | closed\_won\_value | 21000.00 | currency |
| 2026-06-08 | 2026-03-09 | channel | linkedin | closed\_won\_value | 14000.00 | currency |

Cost per closed-won for the March cohort is then March's `ad_spend` divided by every `closed_won` row whose `attributed_date` falls in March, whenever those deals actually closed. Filtering on `date` instead gives you June's spend over June's closes, which is the number all three pages warn against.

<Warning>
  A cohort read is never final. Deals from a recent cohort are still open, so its cost per closed-won will only ever fall as more of them close. Read a cohort against cohorts of the same age, not against last month, and mark rows from an incomplete cohort with `is_estimate` set to `true`.
</Warning>

### Fractional credit

The rows above carry `0.6` and `0.4` against a metric whose unit is `count`, which looks like it breaks the whole-number rule in the checks below. It is a deliberate exception, and it is the only one.

Where an attribution model splits one outcome across several channels, the credit is fractional by definition. One deal influenced by two channels is not two deals. The alternative, giving one channel the whole deal, is a single-touch model, which is a legitimate choice and a different one.

| Rule | Detail |
| :-- | :-- |
| Which metrics may be fractional | Outcome counts that an attribution model splits: `closed_won`, `leads`, `mqls`, `conversions` |
| Which may never be | Platform-reported counts: `impressions`, `clicks`, `sessions`. Nothing splits those |
| What the fractions must do | Sum to the whole outcome across all channels for that `attributed_date`. Two channels on one deal sum to 1.0, not 0.5 and 0.6 |
| Where the model is recorded | The `ATTRIBUTION APPLIED` line of the metric's block in the [data dictionary](/marketing-reporting-data-dictionary), not per row |
| Rounding | Store at least two decimal places. Rounding 0.33 three ways loses a deal every three deals |

<Info>
  Recording the model once per metric rather than once per row is what keeps this honest. A file where some rows were split one way and some another, with nothing saying which, produces a total that is correct only by accident.
</Info>

### Splitting the product out of the campaign name

`product` duplicates something already inside `campaign`, which looks like it breaks the rule two sections down about never storing a value you can derive. It doesn't, and the difference is worth being precise about.

That rule protects against a **derived metric** going stale: store `cost_per_click` and then correct `clicks`, and the two disagree with nothing to say which is right. Dimensions have no such failure mode, because [a name is never changed after launch](/campaign-structure-best-practices#dont-rename-anything-after-launch). The string the product was split out of cannot move underneath it.

What you gain is that the split happens once, at import, under one rule, instead of every report re-parsing a compound string and each one drawing the boundary slightly differently. A report that has to run `SPLIT(campaign, "-")` before it can group by product is a report that will eventually group by the wrong segment.

### Which columns your business needs

This file has a fixed core and a set of extensions. Which extensions apply depends on how your business converts, not on how thorough you are.

| Column | Add it when |
| :-- | :-- |
| `campaign`, `ad_group`, `ad` | You report below channel level. Almost everyone eventually |
| `product` | You sell more than one thing and would ever move budget between them. See [product pages](/product-catalog) |
| `experiment_id` | You run tests or pilots |
| `attributed_date` | Results arrive later than the spend that caused them: any sales-led business with a pipeline, and any subscription business reporting on payback |

**Ecommerce and sales-led businesses need different extensions**, and this is the main place the difference shows up:

| | Ecommerce | Sales-led |
| :-- | :-- | :-- |
| Outcome arrives | Same week as the spend, mostly | Weeks or months later |
| `attributed_date` | Rarely needed | Required, or cost per closed-won is wrong |
| Fractional credit | Uncommon, one session one order | Normal, several channels touch one deal |
| Outcome metrics | [Ecommerce starter pack](/ecommerce-metrics-starter-pack) | [Sales-led starter pack](/sales-led-metrics-starter-pack) |
| Where deal data comes from | The store platform | The CRM, see [where the values get stored](/utm-standards#7-where-the-values-get-stored) |

Adding a column later costs nothing structural. You start filling it from that day forward, and older rows keep whatever they were collected with.

### Only store the grains you report on

Every extra grain multiplies the row count: a day with 40 campaigns, 120 ad groups, and 400 ads carries roughly 560 rows per metric instead of one.

| Store | If |
| :-- | :-- |
| `channel` | Always. Weekly, monthly, and business reporting all read this grain |
| `campaign` | You report per campaign, per product, or on any pilot or experiment carried at campaign level |
| `ad_group` | A recurring report or an experiment needs the ad set level |
| `ad` | An experiment targets creative, or ad-level reporting is a standing need |

Adding a grain later costs nothing structural. You start writing the extra rows from that day forward, and history stays at whatever grain it was collected at.

### The base grain is a day

Each row covers one day, and every report is a date-range filter over the rows: a week, a calendar month, a quarter, or any range you need, such as October 2 to November 1. Nothing ties a report to period boundaries the file holds, because the file holds none.

Daily rows were the expensive option when a person loaded the file by hand, so teams loaded weekly and accepted the rough edges: month-to-date reads, weeks straddling a month boundary. An agent filling the file each morning removes the loading cost, and the rough edges with it. Reporting cadence is a separate choice: the weekly report stays the shortest written report, because day-over-day movement is mostly noise. If you do load by hand, weekly loading still works; write the week's totals as one row dated the Monday of that week, and keep the choice consistent.

### Daily fill and restatement

When an agent loads the file, it writes yesterday's rows each morning: one row per metric, per channel, per grain you store. Conversion metrics settle over several days, so recent rows carry `is_estimate` set to `true` and get restated in place once the platform's figures settle; spend and impressions settle fast and rarely need the flag. Record the restatement window in the [data dictionary](/marketing-reporting-data-dictionary), and treat a restatement as an update to the row, never a second row.

### `blended` is a real channel value, not a summary row

Business-level metrics, total revenue, total marketing spend, contribution margin, aren't attributable to one channel, so they get their own `blended` rows rather than living implicitly as a sum of the channel rows. This is what stops someone accidentally summing a per-channel ratio (like ROAS) into a meaningless blended number; ratios like that have to be recalculated from blended inputs, never summed from channel-level ratios.

A blended row sits at `channel` grain with `channel` set to `blended`, and every dimension column blank. There is no campaign behind total revenue.

### Store the inputs, never the calculated numbers

Store `ad_spend` and `clicks`. Don't store `cost_per_click`. Calculate it fresh, every time you need it, from the two numbers you actually stored. If a derived number gets stored and one of its inputs is later corrected, the two quietly disagree and nothing in the file tells you which one is right.

| Always store | Never store, always calculate |
| :-- | :-- |
| Ad spend, impressions, clicks | Cost per click, cost per mille |
| Purchases, revenue | Return on ad spend, conversion rate |
| New customers, total revenue | Average order value, marketing efficiency ratio |
| Cost of goods, shipping, fees, discounts | Contribution margin |

See the [formula blocks in the data dictionary](/marketing-reporting-data-dictionary#metric-formulas) for how each derived number gets calculated from its inputs, and the [ecommerce](/ecommerce-metrics-starter-pack) and [sales-led](/sales-led-metrics-starter-pack) starter packs for a ready-made list of common inputs and the metrics they produce.

<Info>
  One exception, and it is worth naming because the rule above reads as absolute. A few metrics are aggregates of a grain this file does not hold: `pipeline_value` is summed from individual CRM deal records, and `sales_cycle_days` is averaged across deals. Neither can be recalculated from anything in the flat file, because the deal-level rows live in the CRM. Store them as inputs, and record in the [data dictionary](/marketing-reporting-data-dictionary) which system computed them and over what set, so the number can be reproduced where it was made.
</Info>

## A worked day

One day at two grains, showing how the same money appears once per grain. Dimension columns are trimmed to the ones that carry values here; a real file keeps all seven.

**Channel grain.** What every report reads, over whatever date range it covers.

| date | grain | channel | metric | value | unit | source | campaign | product |
| :-- | :-- | :-- | :-- | :-- | :-- | :-- | :-- | :-- |
| 2026-06-08 | channel | meta | ad\_spend | 61400.00 | currency | meta\_ads |  |  |
| 2026-06-08 | channel | meta | purchases | 712 | count | meta\_ads |  |  |
| 2026-06-08 | channel | google\_search | ad\_spend | 28900.00 | currency | google\_ads |  |  |
| 2026-06-08 | channel | blended | total\_revenue | 103000.00 | currency | shopify |  |  |
| 2026-06-08 | channel | blended | cogs | 37100.00 | currency | finance\_export |  |  |

**Campaign grain.** The same Google spend, split across the campaigns that make it up.

| date | grain | channel | metric | value | unit | source | campaign | product | experiment_id |
| :-- | :-- | :-- | :-- | :-- | :-- | :-- | :-- | :-- | :-- |
| 2026-06-08 | campaign | google\_search | ad\_spend | 17300.00 | currency | google\_ads | Google-FBS-Search-Trial-tCPA-DAPRO-TOFU | DAPRO | |
| 2026-06-08 | campaign | google\_search | ad\_spend | 8200.00 | currency | google\_ads | Google-FBS-Search-Trial-tCPA-DASTART-TOFU | DASTART | |
| 2026-06-08 | campaign | google\_search | ad\_spend | 3400.00 | currency | google\_ads | Google-AO-Search-Leads-tCPA-BRAND-BOFU | BRAND | PILOT04 |
| 2026-06-08 | campaign | google\_search | purchases | 214 | count | google\_ads | Google-FBS-Search-Trial-tCPA-DAPRO-TOFU | DAPRO | |

The three campaign-grain `ad_spend` rows add to 28,900, the channel-grain figure. **That is why they are never summed together.** A pivot that doesn't filter on `grain` reports 57,800 of Google spend on a day that had 28,900.

With the `product` column populated, "what did we spend on Analytics Pro this period?" is a filter on one column: `grain = campaign`, `product = DAPRO`. Without it, that question needs someone to read campaign names and add up by hand.

Note what's absent: no `cost_per_click`, `roas`, or `contribution_margin` rows. Those get calculated when a report needs them, not stored.

## Rolling days up into weeks, months, quarters, and years

A period total is every matching row, filtered to the dates that fall in that period, added together, with every ratio then recalculated from the summed totals rather than averaged from smaller-period ratios. Any date range works the same way: a Monday-to-Sunday week, a calendar month, a quarter, or October 2 to November 1. A spreadsheet pivot table does this in a few clicks:

1. Select the whole flat file range.
2. Insert a pivot table.
3. **Filter `grain` to a single value.** Do this first, before anything else. A pivot spanning two grains double-counts every number it touches.
4. Set **rows** to `metric`, **columns** to `date`, grouped into weeks or months in the pivot (or filter to a channel first if you want one channel's view).
5. Set **values** to sum of `value`.
6. Filter `channel` to the one you want, or leave it as a row field to compare channels side by side.

That gives you the wide, human-readable table.

To report per product, per campaign, or on a single test, keep step 3 and change step 4:

| Question | Filter | Rows |
| :-- | :-- | :-- |
| Spend by product | `grain = campaign` | `product` |
| Spend by campaign | `grain = campaign` | `campaign` |
| One pilot's or experiment's rows | `grain = campaign`, `experiment_id = PILOT04` | `metric` |
| Creative performance in a test | `grain = ad`, `experiment_id = TEST01` | `ad` |

For any rollup, filter the pivot's date range to the period's dates and let the sum do the adding up. Then recalculate every ratio (ROAS, conversion rate, contribution margin) from the summed totals shown in the pivot, exactly as the [monthly report template](/monthly-report-template) walks through.

See [data quality and rollup concepts](/data-quality-and-rollup-concepts) for a worked example of why summing first and recalculating after is the only version of this that produces a correct number.

## Checks before you trust new rows

Run through this list before using new rows in a report. The checks are testable assertions: a person can scan for them, and the agent that loaded the rows can run them on every fill.

**Structural**

- Every row has all eight core columns filled in.
- `date` is a valid calendar day in `YYYY-MM-DD` form.
- `grain` is one of `channel`, `campaign`, `ad_group`, `ad`.
- Dimension columns are filled down to the row's grain and blank below it. A campaign-grain row with an `ad` value is a row at the wrong grain.
- `channel` matches your approved list in the data dictionary's source of truth section.
- `metric` matches a metric defined in the data dictionary's formula blocks.
- No duplicate rows for the same date, grain, channel, metric, and dimension set. A restatement updates the existing row.
- `value` is a bare number: no `$`, no `%`, no commas.

**Dimensions**

- Every `campaign` value matches a live campaign name character for character, and matches its `utm_campaign`. A near-match is a broken join, not a typo.
- Every `product` value exists in your [product pages](/product-catalog). A value that doesn't is a product somebody invented at build time.
- Every `experiment_id` matches a registered ID in the experiment log. An unregistered ID belongs to a test nobody briefed.
- The dimension columns were split at import under one rule, not typed in per report.

**Logical**

- Percent values look like percentages, not decimals. A 3.44% conversion rate is stored as `3.44`, not `0.0344`.
- Counts are whole numbers, unless the metric carries fractional attribution credit. See [fractional credit](#fractional-credit) for which metrics may, and what the fractions have to sum to.
- `clicks` is less than or equal to `impressions`.
- `purchases` is less than or equal to any funnel stage above it (checkouts, add-to-carts).
- No gaps: every day has a full set of rows for every channel you track.

**Cross-checks**

- Spend matches what the ad platforms themselves report for the same dates.
- `total_revenue` matches your approved source of truth.
- Sum of channel-level `conversion_value` sits within the normal gap you recorded against `total_revenue` in the data dictionary; it should be lower, never higher by an unusual margin.
- For any grain you store below `channel`, its rows sum to the channel-grain figure for the same date and metric. A gap means a campaign is missing from the file or one is being counted twice.

If a check fails, fix it before building anything on top of that day's data. An error caught here costs a few minutes. The same error found after it's already shaped a report costs a great deal more.

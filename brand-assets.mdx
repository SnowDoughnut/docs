## Core sections

### 1. Source of truth

**Where do the current files live?** Paste the link to the folder.

_E.g. [Doughnut Labs brand folder](https://drive.google.com/drive/folders/doughnut-labs-brand), mirrored to a public press kit for logos only._

**What is the rule about using files from anywhere else?**

_E.g. Files pulled from a deck, a screenshot, a website, or an email attachment are not approved, however recent they look. If it isn't in the brand folder, it isn't current._

<Accordion title="Concept review: Source of truth">
  Duplicate copies are the mechanism by which a brand quietly goes out of date. A file gets attached to an email, saved to a desktop, dropped into a shared deck, and each copy keeps working long after the original has been replaced. Nothing signals to the person holding the copy that it's stale.

  A single location only holds when it's convenient. If the approved path is slower than reusing a file someone already has, the copies win, and the register becomes a description of what should be happening.

  Brands differ on how open that location should be. A fully public press kit removes almost all friction and removes control over who downloads what. A gated system does the reverse. Most end up splitting the two, with the logo treated as public and everything else gated.
</Accordion>

### 2. Asset register

One row per asset. The file stays in the drive. The register records where it is, who owns it, and any limits on its use.

Type is one of Brand, Creative, Video, Copy, or Other. This page lists the Brand rows. Creative, video, and copy assets go in the same register, so there is one place to check whether something exists.

| Asset | Type | Link | Owner | Usage limits | License expires | Review date |
| :-- | :-- | :-- | :-- | :-- | :-- | :-- |
| _E.g. Primary logo_ | _Brand_ | _/brand/logo/primary_ | _Brand lead_ | _None_ | _None_ | _Annually_ |
| _E.g. Symbol_ | _Brand_ | _/brand/logo/symbol_ | _Brand lead_ | _Avatars, favicons, app icons_ | _None_ | _Annually_ |
| _E.g. Brand typefaces_ | _Brand_ | _/brand/type_ | _Design lead_ | _Internal and contracted agencies only. Not redistributed to partners_ | _Renews annually in March_ | _At license renewal_ |
| _E.g. Product screenshots_ | _Brand_ | _/brand/product_ | _Product marketing_ | _Marketing and sales_ | _None_ | _Every release_ |
| _E.g. Customer photography_ | _Brand_ | _/brand/photography_ | _Brand lead_ | _Named customer, marketing use only, no paid media_ | _Two years from shoot date_ | _At consent expiry_ |
| _E.g. Slide template_ | _Brand_ | _/brand/templates_ | _Brand lead_ | _All internal use_ | _None_ | _Annually_ |
| *Add a row* |  |  |  |  |  |  |

**Who checks usage limits before an asset is used in paid media?**

_E.g. The person building the campaign checks the register. Anything with a usage limit or an expiry date goes to the brand lead before it runs._

<Accordion title="Concept review: Asset register">
  The owner column carries more weight than it appears to. An asset without a named owner has no one to ask when it needs updating, no one to notice when it's wrong, and no one to say yes or no to an unusual request. It ends up maintained by whoever last happened to touch it.

  Review cadence differs by what actually drives an asset out of date, which is why one blanket schedule tends not to fit. A logo changes when the brand changes, which is rare. Product screenshots go stale every time the interface ships. Photography can expire on a date fixed by a consent form regardless of whether anyone looks at it.

  Rights problems surface at the point of scale, not at the point of use. An image sits fine on a blog post for a year and becomes a problem the day it runs as a paid ad, because the license was scoped to something the ad exceeded. Keeping usage limits and expiry dates in the same row as the file puts the answer where the question comes up.

  A register is also the only practical way to answer "does this exist?" Without one, the default answer is to remake the thing, which is how a brand ends up with four slightly different versions of the same diagram.
</Accordion>

### 3. Access

| Group | Can view | Can download | Can edit masters |
| :-- | :-- | :-- | :-- |
| _E.g. Design team_ | _Everything_ | _Everything_ | _Yes_ |
| _E.g. Marketing_ | _Everything_ | _Everything except masters_ | _No_ |
| _E.g. Sales and CS_ | _Logos, templates, screenshots_ | _Same_ | _No_ |
| _E.g. Contracted agencies_ | _Scoped to their project_ | _Same, access expires with the contract_ | _No_ |
| _E.g. Partners and press_ | _Public press kit_ | _Public press kit_ | _No_ |
| *Add a row* |  |  |  |

<Accordion title="Concept review: Access">
  Access controls here are aimed less at secrecy than at preventing accidental edits to shared originals. Most brand files are not confidential. What causes damage is a master being overwritten by someone who meant to save a copy, and the version history nobody checks until months later.

  The agency row is where access most often outlives its purpose. Permissions granted for a project tend to remain after the project ends, because revoking them is nobody's task. Tying expiry to the contract at the point of granting is what avoids relying on someone to remember.

  How far to open the view layer is a real trade-off. Broad visibility means people find what exists and reuse it. Narrow visibility means fewer files leaking into places nobody tracks. Which cost is worse depends on how much of the brand is public anyway.
</Accordion>

### 4. Versioning and retirement

**How is a new version released, and what happens to the old one?**

_E.g. The new file is uploaded to the brand folder with the year in the filename, and the previous version moves to `/brand/archive` with `_retired` appended. Retired files are kept for reference and never used in new work. Retiring anything used externally is announced in the team channel with a date by which the old version should be gone._

**What's currently retired, and where do old versions still appear?**

| Retired asset | Replaced by | Still appears in | Removal owner |
| :-- | :-- | :-- | :-- |
| _E.g. 2019 wordmark_ | _2024 primary logo_ | _Partner directory listings, old case study PDFs_ | _Brand lead_ |
| *Add a row* |  |  |  |

<Accordion title="Concept review: Versioning and retirement">
  Replacing an asset is fast. Removing the previous one from everywhere it already landed is the slow part, and it's the part that determines whether a rebrand actually completes. Old logos persist in partner sites, printed material, email signatures, and third-party directories long after the new one ships.

  Deleting the retired file outright seems tidy and creates a different problem: someone maintaining an old artifact needs to identify what they're looking at, and nothing is worse for that than an asset that no longer exists anywhere. Archiving with a clear marker keeps the reference without keeping it in circulation.

  Tracking where an old version still appears turns retirement from an event into a task with an end. A list with owners can be worked through. An unwritten intention to clean it up eventually usually isn't.
</Accordion>

Every page in this knowledge base carries a short **MCP wiring** block at the bottom. The block is how the MCP finds the page, knows what it supplies, and knows what else to pull when it runs. Readers can ignore it; the collaborator reads nothing else first.

## How discovery works

Pages connect by **capability key**, never by page name.

- **Provides** is what a page supplies: `hook-type`, `copy-framework`, `brand-voice`, `copy-template:meta:carousel`, `process:copywriting`.
- **Uses** is what a page needs. When the MCP runs a process, it pulls every page that provides each key in Uses.
- **A key matches everything below it.** `copy-template:meta` matches every Meta copy template; `copy-template` matches all of them. A process that uses `creative-specs` finds a spec page added next year without being edited.

So a new copywriting framework page that declares `Provides: copy-framework` appears as an option in every copy conversation the day it is published. Nothing else changes.

## How options get ranked

A question with a closed list behind it, such as which hook, which framework, or which report template, can have five options or fifty. The MCP never shows fifty.

1. It reads the **context** from the brief, the setup, and the conversation so far, as values from the facets below.
2. It scores each option by how many of its **Best for** values match the context, and drops any option whose **Avoid when** matches.
3. It offers the **top five**, each with a one-line reason, and ends with "or see all".
4. Ties keep the order the options appear in on their page. Five or fewer options are all shown.

Best for and Avoid when sit in the wiring block for a page that is one option, and in their own columns for a list page where each row is an option, like [hook types](/hook-types).

### Context facets

Best for and Avoid when use only these values, so every option across the framework ranks against the same context.

| Facet | Values |
| :-- | :-- |
| `goal` | awareness, consideration, conversion, retention |
| `offer` | sale, launch, trial, lead-magnet, event, evergreen |
| `audience` | cold, warm, retargeting, customers |
| `length` | short, long |
| `proof` | numbers, reviews, none |
| `channel` | meta, google, linkedin, tiktok, youtube, email, organic-social, web, seo |
| `business` | ecommerce, saas, sales-led, b2b, b2c, local |

A new facet value gets added here first, then used.

## Wire in a new page

Add the block at the bottom of the page, above the endcap if the page has one, and fill in:

1. **Type**, one of the page types below.
2. **Provides**, reusing an existing key from the index when the page supplies the same kind of thing. A new framework is `copy-framework`; a new video skill is `skill:` plus its name.
3. **Best for**, if the page is something the MCP might offer as a choice.

Processes, briefs, and setup pages also get **Triggers** (the requests that route to them), **Asks** (one short question per turn, each naming the key its options come from), and **Output**. The turn-by-turn rules are [how the MCP talks](/mcp-conversation), and the [router](/mcp-router) lists every entry point.

### Page types

| Type | What it is |
| :-- | :-- |
| process | A step-by-step SOP a person or agent runs |
| skill | An agent skill with a runbook |
| brief | A fill-in planning document |
| template | A fill-in output, like a copy template or report template |
| checklist | Checks run before or after something ships |
| list | A closed list whose rows are answer options |
| standard | Rules and best practices to follow |
| concept | The reasoning behind a standard |
| spec | Platform specs and limits |
| library | A register where work is filed and found |
| hub | A landing page for a channel or task |
| setup | Onboarding and setup |
| mcp | Pages about the MCP itself |
